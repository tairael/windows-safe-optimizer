# 写作规范

这份规范只约束 `windows-safe-optimizer` 的公开文字。目标不是让每页语气相同，而是让读者能分清事实、判断、风险和下一步。

## 写出这个项目独有的事实

“安全、强大、全面”不能帮助用户决定是否执行。优先写可核对的对象和边界：R2 启动项在深度协作模式逐项确认；基线脚本只把 JSON 与 Markdown 报告写入用户选择的目录；网络测试要区分 HTTP、SSE 和 WebSocket。

一段话至少应有一个替换成其他优化工具名称后就会失真的事实。不能提供事实时，删去修饰语。

## 先说场景，再解释规则

使用用户真正会说的话开场，例如“C 盘只剩 8 GB”或“网页能开但一直重连”。紧接着指出常见误判、要收集的证据和停止条件。不要从行业趋势、技术进步或“电脑在日常生活中不可或缺”开始。

## 区分四种句子

- **事实：**写出来源、时间、范围或测量条件。
- **推断：**说明证据为什么支持它，同时保留不确定性。
- **建议：**标出适用对象、风险等级和模式门禁。
- **结果：**同时写指标和功能复测，不把命令成功当成优化成功。

## 让风险可操作

不要只写“操作有风险”。说明可能失去什么、哪个对象会受影响、备份在哪里、如何回退、什么现象触发停止。禁止级动作直接命名，不用含糊的“谨慎使用某些工具”。

## 保持自然节奏

段落负责解释因果，列表只承载真正并列的项目。句子可以短，也可以在需要限定条件时变长；不要把每节都写成三条、每条都用相同动词开头。避免连续使用“此外”“同时”“值得注意的是”和重复结论。

中文使用自然标点。英文标题采用 sentence case；包名和模式名始终写作 `windows-safe-optimizer`、`conservative-advice` 和 `deep-collaboration`。R0–R4、PowerShell、OneDrive、WebSocket 等技术词在能减少歧义时保留英文。

## 案例与数字

单机案例必须注明设备和场景限制。空间变化要区分文件逻辑大小与卷可用空间；内存数字要写重启、静置和用户上下文；代理结果要写测试协议与持续时间。案例展示方法，不承诺别人复制相同收益。

## 发布前检查

1. 每个建议是否有范围、风险、回退、验证和停止条件？
2. 是否把设备名、用户名、SID、组织、公网地址、真实代理 URL 或本机路径带进公开内容？
3. 是否把第三方安装器与 Skill 自身的联网、遥测边界混在一起？
4. 链接、Mermaid、SVG、命令和 Windows 生命周期陈述是否仍然成立？
5. 结尾是否给出下一步，而不是换一种说法复述整页？
